# Sprint 15 — accessibility, monitoring and recovery measurements

Scope: Phase 1 S15. This change adds keyboard and automated accessibility checks, protected route histograms, a bounded synthetic load smoke, a Redis readiness drill, and timed database restore / compatible-release rollback reports. It does not establish a customer capacity envelope or certify WCAG conformance. Published-head CI evidence must pass before implementation acceptance.

## Accessibility

Custom dialogs keep focus inside the active dialog, make surrounding content inert, close on Escape and restore the opening control (or the workspace main region if the opener was removed). Inline callback changes do not reset form focus. Native modal dialogs retain their browser focus behavior. Mobile navigation uses the same keyboard lifecycle below 801px; its closed controls are hidden. The profile menu supports arrows, Home, End, Escape and normal Tab exit. Focus indicators, scroll margins, reduced motion and forced-color outlines use the existing design tokens. Shared metric/empty-state text has sufficient contrast and the CEO definition list has valid groups.

The browser suite runs axe WCAG A/AA rules against eight role overviews and keyboard cases for a 360px mobile sidebar, profile menu, employee/termination/Insights forms, connection recovery, nested mobile profile keys and a 768px privacy dialog with reduced motion. Synthetic empty/unavailable responses are fixtures, not evidence of production datasets. No violations are suppressed. These checks supplement existing authenticated browser coverage; they do not replace manual screen-reader, zoom, forced-color and populated workflow acceptance.

## Monitoring and bounded load smoke

The existing private Actuator endpoint exposes HTTP latency histograms at 100ms, 500ms, 1s and 2s, plus JVM and connection-pool metrics. System Admin authorization remains required for metrics; the public proxy continues to return 404 for Actuator. Anonymous readiness responses expose status only. Readiness includes PostgreSQL and Redis. Liveness excludes these dependencies to avoid restart loops. The disposable drill verifies anonymous/employee denial, admin metrics, Redis loss returning readiness 503 while liveness remains 200, then recovery to readiness UP.

`ops/staging/verify.sh` requires an explicitly disposable localhost stack and begins with an empty account database. The API fixture creates exactly 500 synthetic accounts and exercises 50 distinct active sessions with one paced request per session per second. Fixed operations mix dashboard, workboard and preference reads with a Team Lead worksheet creation every eighth operation. Requests use the real HTTPS proxy and API; no mutation retries occur. Fixture JWTs use the disposable signing key in memory and are never written to reports. This bypasses login/refresh/MFA journeys and must never be used against customer data.

The default smoke lasts 30 seconds; `STAGING_LOAD_SECONDS` permits 30–120 seconds within the existing privileged proof lifetime. A separate customer soak must use genuine login, refresh and step-up sessions. Reports retain fixed operation labels, sample counts, HTTP status/error counts, p50/p95/p99/max, elapsed time and asynchronous CPU/memory/active-query/lock-wait samples. Network errors count as status 0. Samples are bounded and percentiles require at least 100 observations per operation to describe target passage. Insufficient samples cannot pass measured targets. CI requires an error-free complete smoke and a core mutation; a short smoke is not a capacity certification.

Artifacts are `load-report.json`, `monitoring-report.json` and `recovery-report.json` in the existing secured evidence directory. Only these aggregate reports and existing safe text evidence are uploaded, including on a failed run. No tokens, business response bodies, database dumps, private keys or container environment are uploaded.

## Restore and compatible-release rollback

The disposable drill builds the current immutable release and the independently built, previously verified Sprint 14 release `a247b2f70818dd397fb842857014ef8995a08808`. After API verification it stops backend writes, creates deterministic recovery probes, takes a checksummed logical database backup and restores into a separate database. Matching Flyway checksums and retained fixture fingerprints are required before the restored current app starts. It then starts the actual Sprint 14 backend/frontend images against the restored compatible V70 database, checks TLS and authorization, reads a retained worksheet through the authenticated application, and reapplies the current images against the original database and verifies the same retained worksheet again. No schema down-migration is performed.

Monotonic clocks report installation, backup, restore, outage-to-restored-readiness, prior-release rollback and current-release reapply times. Timing fields are rejected unless ordered and associated with distinct immutable release SHAs. A quiesced rehearsal can establish zero lost fixture rows; customer RPO remains unknown. Database-only recovery excludes off-host retrieval, WAL/PITR, private objects, archive/encryption keys, DNS, host replacement and provider state. Retain those components under the existing secured recovery runbook before any production rehearsal.

## Outstanding release acceptance

1. On the chosen customer-like deployment, run a representative 500-account, 50-concurrent-session, three-tab, 60-minute mix with real session renewal and mutation distribution. Record infrastructure sizing, dataset distribution, operation counts, CPU/memory/pool/lock behavior and errors. Require read p95 ≤500ms, core mutation p95 ≤1s, API p99 ≤2s and error rate <1%. Investigate long tails; record the measured supported envelope.
2. Complete keyboard and screen-reader checks in Chrome, Firefox and Safari on populated visits, work, HR, approvals and error/recovery paths; test 200–400% zoom, narrow viewports, reduced motion, high contrast and focus unobscured by sticky content. Record versions, findings and owner signoff.
3. On a separate secured host, retrieve backups, restore database/private objects/archive/key versions and service configuration, rehearse a failure and compatible rollback under representative writes, measure data loss and elapsed recovery, and obtain approved RPO/RTO targets. A short logical restore is not full disaster recovery.
4. Carry forward Google Calendar/Slack live acceptance and selected tablet/scanner/printer UAT from Sprints 12–14. Kiosk remains disabled by default. Commercial readiness stays gated by these supervised results.
