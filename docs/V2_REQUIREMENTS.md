# V2 requirements and release gates

Companion to [PRODUCT_ROADMAP.md](PRODUCT_ROADMAP.md). Proposed requirements below are backlog items, not claims about implemented behavior. Sprint S0's completed fixes and current limitations are in [V2_AUDIT.md](V2_AUDIT.md).

## Implementation contract

Preserve appointment/approval/Workboard/account lifecycle behavior and the existing design tokens, spacing, typography, responsive patterns and formats. A new feature owns its page/components, state hook, API and contracts under `frontend/features/<feature>/`; thin routes register it, and shared transport stays in `frontend/lib/api-client.ts`. For Workboard, use its existing feature folder. Avoid another root file accumulating unrelated screens or an untyped all-service controller.

Keep the backend modular monolith: domain-owned application services and persistence, public `api` interfaces/events for inter-module calls, transactions for business writes, and durable after-commit delivery. Proposed new integration, site, emergency and platform modules must declare their dependencies before implementation. Do not add a frontend database access path. New Flyway migrations are additive; never edit a migration already applied to a customer database.

Product owner approves workflows and policies; engineer owns implementation/regression evidence; QA or a second reviewer validates role and scope boundaries; operations owns deploy/restore/monitoring; customer administrator supplies provider/device access and UAT. Independent security assessments require an external reviewer. A solo engineer still needs those inputs.

## Release gates

All numbers here are **proposed acceptance targets**, not current measured performance or contractual guarantees. Agree the workload, hardware and exclusions before testing.

| Gate | Required evidence |
| --- | --- |
| Every sprint | CI passes frontend audit/typecheck/lint/build/regressions/browser tests and backend verification; reviewed migration/rollback, role/scope tests, API contracts, loading/error states, and visual comparison for touched screens. No new critical/high dependency finding. Secrets and tokens absent from logs/client artifacts. |
| Supervised pilot after S4 | Staging install/restore/rollback exercised; AUD-01/02 addressed; company setup/onboarding usable; core appointment/Workboard/account tests pass; known limits and support contact accepted. Integrations/kiosk may remain manual and are not advertised as delivered. |
| Phase 1 / V2.0 | Representative 500-account dataset; at least 50 concurrently active sessions, three-tab scenario and agreed visit burst for a 60-minute mixed workload. Proposed targets: common API read p95 ≤500 ms, core mutation p95 ≤1 s, common API p99 ≤2 s, non-induced error rate <1%. Exclude SMTP/provider/printer latency and separately measure queue delivery. Record CPU/memory/DB saturation, recover after induced Redis/provider outages, prove metrics freshness and scoped cache. RPO/RTO measured, second install under one working day and admin setup target ≤30 minutes demonstrated, two pilot UATs complete. |
| Phase 2 | Customer-agreed peak/site/IdP/vendor workload and SLA measured; site/role isolation, SSO/SCIM revocation, signing/door behavior and emergency drill accepted. Independent pen-test/retest passes; DR exercise validates negotiated RPO/RTO. No generic enterprise certification claim. |
| Phase 3 | Independent cross-tenant review; adversarial isolation and noisy-neighbor tests; tenant lifecycle/restore/export and regional boundary proof; billing reconciliation and support access audit; paid pilot; operational on-call/incident and customer exit plans tested. |

For latency tests, define endpoint mix, warm/cold cache, time zone/date ranges, file/report sizes and data volume. Dashboard averages and an idle load test do not establish p95/p99. Keep a versioned report with test script, dataset seed, topology, results and regressions.

## Definition of ready and unresolved inputs

Before S1: cloud/region, DNS owner, SMTP provider, backup retention and operations owner. Before S5: first calendar and messaging providers chosen by pilot demand; customer test accounts and consent owner. Before S8: tablet/browser/printer model and badge paper size. Before E1/E7/E10: IdP tenant, signing workflow, vendor access/simulator, site policies and revocation expectations. Before Phase 3: tenant isolation design, supported jurisdictions/regions, billing provider, pricing/entitlements and staffed support.

These are implementation inputs to resolve at their sprint boundary; they do not prevent the current audit, regression fixes or roadmap from being completed. Unresolved vendor access should result in a simulator and a clear blocked UAT gate, not a claim of live integration success.
