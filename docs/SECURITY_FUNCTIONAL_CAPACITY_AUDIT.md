## Capacity findings that still gate a large deployment

“Lakhs of client records”, “lakhs of simultaneously connected clients” and “many isolated customer companies” are different workloads. This application is currently single-company. These changes do not create SaaS tenant isolation or prove any concurrency ceiling.

| Constraint | Concrete next implementation / proof |
| --- | --- |
| Several approval/leave lists and startup cancellation still use unbounded lists | Introduce paged queue contracts with visible totals/next-page controls. Batch cancellation in short, locked transactions with a bounded catch-up scheduler. Do not silently truncate queues or keep a growing ORM session across batches. Paths: `AccountProvisioningService.pending`, `LeaveRequestService.mine/pending`, `EmployeeTerminationService.pending`, `RoleDepartmentChangeService.pending`, `AppointmentService.cancelPastUnfinishedVisits`. |
| Realtime is instance-local and heartbeat checks scale with open streams | Introduce a bounded cross-replica invalidation path with current account/department scope, coalescing and backpressure; test two real app replicas, revoked sessions, leases and slow consumers. Keep signals free of business payloads. The local coalescer fixes mutation-thread amplification only. |
| Bulk imports lock authority/assignment tables in SHARE mode | Measure concurrent imports against permission changes and task/appointment writes. Replace global locks only after demonstrating a consistent per-account/reference locking/version strategy across writers. Removing the locks without replacement would weaken security. |
| Async listeners and remote calls can saturate bounded pools | Verify rejected-task handling and durable replay. Move important effects to existing durable outbox ownership rather than adding an in-memory queue or unbounded executor. Exercise stalled SMTP/provider responses, worker restarts and uncertain acknowledgements. |
| Database pool, indexes and summaries have no customer workload measurement | Run query plans on realistic skew, cold/warm caches, date ranges and payload sizes. Cap total connection budgets across replicas before changing the default pool of fifteen per instance. Measure locks, slow queries, vacuum and storage growth. |
| Multi-company isolation is not implemented | Do not share the current installation among independent tenants. Follow the existing tenant-isolation roadmap for SQL, files, caches, sessions, jobs, exports, channels and support access; require adversarial isolation proof before SaaS use. |
| Operational and release proof remains pending | TLS, real-host recovery, object/archive/key recovery, alert/escalation ownership, two pilots, support acceptance and the fourteen human gates still require actual evidence. Branch metadata read during the audit also showed `protected: false`; required status-check policy should be established before accepting failed/unreviewed merges. No repository policy was changed. |

### Representative load and failure campaign

Use a disposable staging deployment with the same PostgreSQL, Redis, brokers, object storage, scanner and proxy configuration as the proposed customer topology. Use synthetic data only and record its seed and distribution. Existing `scripts/run-large-data-performance-tests.sh` remains available for the history query check; ordinary backend CI now requires it as part of the full suite when Docker is present.

1. The existing 3.5-million-row history fixture passed in CI. Next prove representative 100,000 client/visitor records and at least one million visits/history entries with department and time-range skew.
2. Ramp active sessions in agreed stages, for example 100, 500 and 1,000. Increase only after measured resource and latency criteria pass; these are test stages, not promised capacities.
3. Hold a mixed workload for at least sixty minutes: login, refresh/MFA renewal, search, approvals, work updates, visitor intake/check-in/out, notifications and bounded exports. Include three-tab behavior and slow SSE consumers. The existing short 50-session smoke drill is not this soak.
4. Record per-endpoint p95/p99 and error rate, database pool/locks/slow queries, Redis latency/failure, outbox age, heap/GC, CPU, network and storage. The existing Phase 1 proposed targets remain read p95 ≤500 ms, core mutation p95 ≤1 s, p99 ≤2 s and non-induced errors <1%; these need customer agreement and actual measurements.
5. Induce Redis/provider/scanner outages, duplicate/reordered jobs, an app/worker restart during a claim, expired sessions and database contention. Verify fail-closed authorization, durable no-effect rejections, bounded retries, recovery and no cross-scope data exposure.
6. Run two replicas and the promised host-failure topology before claiming horizontal scaling or HA. Three Kafka brokers on one host do not establish host availability. Record genuine RPO/RTO and customer/operator sign-offs after recovery.

The isolated 3.5-million-row fixture is passed; the remaining representative soak, failure, topology and customer-acceptance stages are not marked passed.
